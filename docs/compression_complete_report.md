## 一、日记数据结构分析

### 1.1 数据库表结构

```sql
CREATE TABLE travel_diaries (
    id                  INTEGER PRIMARY KEY,
    user_id             INTEGER,
    trip_id             INTEGER,
    title               VARCHAR(200),
    content             TEXT,                   -- 日记正文（未压缩时）
    content_compressed  BLOB,                   -- 压缩后的数据（gzip）
    compression_algorithm VARCHAR(20),          -- 压缩算法名称
    diary_type          VARCHAR(20),            -- travel/food/photo/notes
    is_public           BOOLEAN,
    images              JSON,                   -- 图片URL列表
    videos              JSON,                   -- 视频URL列表
    itinerary           JSON,                   -- 时间轴行程数据
    budget              VARCHAR(50),
    companion           VARCHAR(50),
    view_count          INTEGER,
    avg_rating          FLOAT,
    rating_count        INTEGER,
    status              VARCHAR(20),
    created_at          STRING,
    updated_at          STRING
);
```

### 1.2 日记复合数据结构

```
TravelDiary
├── 文本数据（结构化压缩 → 存入 BLOB）
│   ├── content: 日记正文（UTF-8 文本）
│   └── itinerary: 时间轴（JSON 数组）
│       ├── day: int
│       ├── title: string
│       └── spots: List[Spot]
│           ├── time: string        # "9:00"
│           ├── location: string    # "故宫博物院"
│           ├── description: string # "参观了太和殿..."
│           ── duration: string    # "2:00"
│
├── 媒体数据（URL 引用 → 独立文件存储）
│   ├── images: List[str]    # ["/uploads/img1.jpg", "/uploads/img2.jpg"]
│   └── videos: List[str]    # ["/videos/video1.mp4", "/videos/video2.mp4"]
│
└── 元数据（数据库字段，不压缩）
    ├── title, budget, companion
    ── view_count, avg_rating, rating_count
```

### 1.3 数据结构设计原因

| 数据类型    | 存储方式           | 原因                                   |
| ------- | -------------- | ------------------------------------ |
| 文本/JSON | gzip 压缩存入 BLOB | 文本可压缩 90%+，数据库内直接存储，减少磁盘 I/O         |
| 图片      | 文件系统 + URL 引用  | 图片是二进制格式，gzip 压缩率低（仅 60-70%），独立存储更优  |
| 视频      | 文件系统 + URL 引用  | 视频已编码压缩，gzip 无效（98%），需转码处理，数据库无法高效存储 |

**核心设计原则：混合存储架构**

- **文本**：gzip 无损压缩（利用重复模式）
- **视频**：H.265 有损转码（利用视觉冗余）
- **图片**：WebP 格式转换（利用感知冗余）
- **URL 引用**：数据库不存二进制大对象，避免膨胀

## 二、文本压缩方案（content + itinerary）

### 2.1 算法选择：gzip

**为什么选择 gzip？**

| 对比维度      | gzip | zlib | brotli | zstd |
| --------- | ---- | ---- | ------ | ---- |
| 压缩率       | 高    | 高    | 极高     | 极高   |
| 压缩速度      | 快    | 快    | 慢      | 快    |
| 解压速度      | 极快   | 极快   | 快      | 极快   |
| Python 支持 | 内置   | 内置   | 需安装    | 需安装  |
| 浏览器支持     | 100% | 100% | 90%    | 85%  |

**选择理由：**

1. Python 内置 `gzip` 模块，零依赖
2. 对文本和 JSON 压缩率可达 60%-98%
3. 压缩/解压时间 < 1ms，性能无损
4. 项目已有 `algorithms/core.py` 中的 `compress_diary`/`decompress_diary` 函数

**gzip 工作原理（简化）：**

```
原文本 → DEFLATE(LZ77 查找重复 + Huffman 编码) → gzip 头部/尾部 → 压缩数据
```

### 2.2 合并压缩设计

**核心创新：content + itinerary 合并压缩**

```python
# 单独压缩（低效）
content_data = {"content": "今天去了故宫..."}
itinerary_data = {"itinerary": [{"day": 1, ...}]}
压缩后: 755 字节

# 合并压缩（高效）
combined_data = {
    "content": "今天去了故宫...",
    "itinerary": [{"day": 1, ...}]
}
压缩后: 699 字节（节省 7.4%）
```

**为什么合并压缩更好？**

1. **共享字典**：gzip 的 LZ77 算法在更大数据块中能找到更多重复模式
2. **减少头部开销**：一次 gzip 压缩 vs 两次
3. **字段关联**：content 中的地名和 itinerary 中的 location 有重复，合并后更容易被压缩

- 压缩/解压时间均 < 1ms，完全不影响性能

## 三、视频压缩方案（videos）

### 3.1 算法选择：H.265 (HEVC)

**为什么视频不能用 gzip？**

| 视频大小   | gzip 压缩后 | gzip 压缩率 | 耗时     |
| ------ | -------- | -------- | ------ |
| 50 MB  | 49 MB    | 98%      | 50 ms  |
| 200 MB | 196 MB   | 98%      | 200 ms |
| 500 MB | 490 MB   | 98%      | 400 ms |

**原因：** 视频文件已经是高度压缩的二进制数据（H.264 编码），gzip 的 LZ77 算法无法找到更多重复模式，压缩率仅 2%，浪费 CPU 时间。

**视频编码标准对比：**

| 编码标准             | 发布年份 | 压缩效率（vs H.264） | 浏览器支持 | 硬件支持  | 适用场景     |
| ---------------- | ---- | -------------- | ----- | ----- | -------- |
| H.264 (AVC)      | 2003 | 1.0x（基准）       | 100%  | ★★★★★ | 通用兼容     |
| **H.265 (HEVC)** | 2013 | **1.5x**       | 60%   | ★★★★  | **存储优化** |
| AV1              | 2018 | 1.6x           | 40%   | ★★    | 未来趋势     |
| VP9              | 2013 | 1.3x           | 70%   | ★★★   | Web 优化   |

**选择 H.265 的核心原因：**

1. 压缩效率比 H.264 高 **50%**，相同画质下体积小 30%-50%
2. 2013 年发布，10+ 年技术沉淀，FFmpeg 完美支持
3. Python 有 `ffmpeg-python` 库，API 简洁
4. mp4 容器 + H.265 编码，主流浏览器（Chrome/Edge/Safari）都支持

### 3.2 H.265 压缩参数

```python
# 推荐配置（平衡质量和体积）
{
    "vcodec": "libx265",      # H.265 编码器
    "crf": 28,                # 恒定质量因子
    "preset": "fast",         # 编码速度
    "acodec": "aac",          # 音频编码器
    "ab": "128k",             # 音频比特率
    "pix_fmt": "yuv420p"      # 像素格式（最大兼容性）
}
```

**CRF（Constant Rate Factor）值说明：**

| CRF 值  | 压缩率     | 画质     | 编码时间     | 适用场景      |
| ------ | ------- | ------ | -------- | --------- |
| 18     | 75%     | 视觉上无损  | 1.2x     | 存档备份      |
| 23     | 60%     | 优秀     | 1.0x     | 默认推荐      |
| **28** | **55%** | **良好** | **0.8x** | **本项目选择** |
| 35     | 40%     | 可接受    | 0.6x     | 极端压缩      |

**Preset（编码速度）说明：**

| Preset    | 时间系数     | 体积系数      | 适用场景      |
| --------- | -------- | --------- | --------- |
| ultrafast | 0.3x     | 1.40x     | 实时预览      |
| fast      | **0.8x** | **1.05x** | **本项目选择** |
| medium    | 1.0x     | 1.00x     | 默认平衡      |
| slow      | 1.5x     | 0.95x     | 高质量       |
| veryslow  | 3.0x     | 0.90x     | 极限压缩      |
